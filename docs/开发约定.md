# 开发约定

本文件记录用户已确认的协作规则。适用于本地定制项目；[功能规则](功能规则.md) 记录业务要求与当前实现，[CHANGELOG](../CHANGELOG.md) 记录实际变更。根目录和源码目录的 `AGENTS.md` 负责新会话的阅读入口。

## 修改前的阅读与核对

每次开始工作先完整阅读本文，并阅读功能规则的状态说明、待处理事项、本次相关条目及专项文档；结合 README、相关版本记录、源码与测试确认现状。不要仅凭聊天记忆或旧文档判断已实现。

已有专项文档保留，作为对应版本的详细说明和验证记录；功能规则汇总统一口径并链接过去。旧文档与当前规则矛盾时，加历史适用范围说明，不把旧方案当成当前实现。

普通文档不会保证在每次新会话中自动加载；`AGENTS.md` 要求工作开始时主动阅读。会话必须在本目录或源码目录的适用范围内，且工具支持该入口机制。

## 先讨论，再授权实施

- 用户提出想法、询问“能不能”“有什么办法”时，先说明完整思路、修改范围、预期行为、边界、验证办法和不确定事项，等用户明确同意后实施。
- “这个规则没问题”等业务确认只确认需求，不单独视为开始写代码、改配置或打包的授权。
- “你看看”“查一下”允许只读调查；先说明只读范围。调查后发现的问题和方案应先告知，不顺便修改。
- 已有明确授权在约定范围内持续有效，完成必要工作，无需重复征求相同许可。新增功能、范围变化或未确认的业务分歧先沟通；可继续不依赖答案的已授权工作。
- “开始创建文件”在本次仅授权文档整理，不授权修改登录、机器人、调度、配置或构建行为，也不授权生成、重命名、替换 EXE。
- 发布、推送外部消息、真实签到等动作按具体授权执行。测试已保存机器人会实际发消息，不能把离线测试当作发送授权。

## EXE 名称和版本

后续交付的 EXE 名称使用 `HDUSign-v<主版本>.<次版本>.<修订版本>-<更新内容>.exe`，例如 `HDUSign-v2.3.1-登录验证修复.exe`。描述应简短、准确，对应最终交付内容。

版本号第一位（如 `2.x.x` 升为 `3.0.0`）变更前，必须先说明原因、影响并取得用户明确同意。普通修复、一般打包授权不包含大版本升级许可。其余版本变更在已获批准的任务范围内执行，并与代码和 Windows 版本资源保持一致。

当前源码及最新交付版本为 `2.3.2`，产物为 `HDUSign-v2.3.2-移除自动签到及机器人复用.exe`。`tools/build_continuous.py` 已采用版本号和更新内容命名，自动编译当前全部项目模块、移除已删除模块，并写入独立版本的 QML；不会覆盖已有同版本产物或其界面目录。2026-10-23 已获准打包并完成离线验收，旧版 EXE、旧版 QML、账号及个人配置保留。后续打包仍须按实际最终变更填写更新内容。

旧文件不因新约定自动更名，保留可回退的发行文件。源码版本统一在 `hdusign/__init__.py` 维护；不要仅修改文件名而误称版本已升级。

## 需求、实现与证据分开

功能规则按“已确认要求／当前实现／验证或待处理事项”记录：

- 已确认要求：用户已认可的预期行为，即使尚未实现也要保留。
- 当前实现：能由当前源码、测试或已交付版本证明的行为，注明限制。
- 待实现：已确认但代码尚未符合的要求；待核查：证据不足、需进一步检查的行为。
- 待验证：已有实现，但尚缺真实场景验证；不能据此宣称验证完成。

发现不一致先明确报告，并记录待处理项。专项方案、测试脚本存在、模拟用例通过不等于功能在真实课堂、真实账号和真实网络下全部验证。

## 测试、交付与文档维护

针对获准修改运行必要检查；低影响纯文档整理检查链接、内容一致性和改动范围，不为此重新登录、推送消息或录制课堂。

代码变更按范围验证，涉及打包时检查冻结程序和实际产物。说明改了什么、如何验证、未验证的真实场景和已知限制；未实际运行的测试不要写成通过。

交付时同步 README 的使用变化、功能规则的实现状态、相关专项文档和 CHANGELOG。CHANGELOG 只记录实际发生的变化；未交付文档放在“未发布”，讨论方案不登记成已交付功能。历史日期无证据时不补造。

不重置、覆盖与本次任务无关的未提交改动，不擅自提交、推送或发布。模型、运行依赖、旧 EXE 和账号数据的变更要在授权范围内。

## 本地资料保护

文档和示例不包含真实密码、Cookie、JWT、Webhook 链接或完整带令牌媒体地址，不复制个人账号配置作示例。DPAPI 加密不意味着同一 Windows 用户下完全不可访问；直播会话仍包含敏感登录凭据。完整运行目录不能作为公开源码包分享。
