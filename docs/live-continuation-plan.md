# 直播分节衔接方案（待实现）

> 历史方案：本文的“待实现”“当前版本”指调查时的旧版本，不代表 v2.3.1。后续已实现的两／三节分组与第三节换流见[连堂课](continuous-lessons.md)，统一规则和验证边界见[功能规则](功能规则.md)。本文保留原始接口调查，不作为当前实现声明。

本文记录已核实的接口事实和后续实现、验证方案。本次没有实现自动换节，没有获取下一节媒体，也没有进行实际切换。当前版本只对用户选择的同一 `courseId` 做有界重连。

## 已核实的两节课

已核实同一教学班的两节关联。下面使用虚构标识和示例时间说明字段关系，不公开实际课程与课表；示例时间均为北京时间（UTC+8）。

| 字段 | 当前节 | 下一节候选 |
| --- | --- | --- |
| `courseId` | `current-course` | `next-course` |
| 教学班 `teclId` | `same-class` | `same-class` |
| 科目 `subjId` | `same-subject` | `same-subject` |
| 教室 `clroId` | `same-room` | `same-room` |
| 学期 `acteId` | `same-term` | `same-term` |
| 节次 `letiNumber` | `n` | `n + 1` |
| 正式上课时间（示例） | 08:00–08:45 | 08:50–09:35 |
| 直播时间（示例） | 07:57–08:47 | 08:47–09:37 |

本次只确认了这两节。第三节及更后面的安排没有验证。

当前节详情来自以下只读请求：

```text
GET /jy-application-resourcemanage/v1/course_vod_videoinfos
courseId=<current-course>
playType=2
```

响应通过 `continueCourId` 给出下一节候选，并返回 `continueCourRefreshTime`。在核验样本中，该时间与下一节正式开课时间相同，晚于下一节直播窗口起点；该字段的完整语义尚未验证，不能直接把它解释为开流时间或强制切换时间。

同教学班列表来自以下只读请求：

```text
GET /jy-application-resourcemanage/v1/vod_live/t-1
page.pageIndex=1
page.pageSize=100
page.orders[0].asc=true
page.orders[0].field=courBeginTime
liveDay=0
teclId=<same-class>
```

列表实际返回了同一下一节候选，其教学班、科目、教室、学期四项一致，节次相邻。本次列表只有一条记录，不能据此认定它是完整全天课表，也不能据此推断不存在第三节。

## 前端证据与尚未确认的行为

- `build/live-inspection/2959.af9261c5.js`：模块 `96885` 导出的 `VT` 对应直播详情 GET。
- `build/live-inspection/index.a7d227f5.js`：实际模块 `1560` 导出的 `vE` 对应 `/v1/vod_live/t-1`。
- `build/live-inspection/2321.0d6b5f30.js`：`LivePlay` 使用 `vE` 按教学班和 `liveDay=0` 读取并渲染节次，使用 `VT` 读取当前详情；结束时进入 `LiveEnd`。这些代码尚不能证明页面已经实现自动续节。
- `coureseTransferFlag` 用于语音功能，不能用作自动续节标志。

上述证据证明了候选关联和节次列表的存在，尚未证明候选在切换时一定可播放。列表分页完整性、第三节关联、`continueCourRefreshTime` 的用途，以及不同课间长度仍需分别验证。

## 拟采用的切换条件

`continueCourId` 只用于发现候选。每次切换之前都重新 GET 候选的直播详情，继续使用 `playType=2`，且所有详情和列表请求限定在已验证登录的同一站点源内。候选必须同时满足以下条件：

1. 候选是单个明确的课程标识，与响应中的课程标识一致，且不在本次监听已访问的标识集合中。不能通过递增 `courseId` 猜下一节。
2. 当前节与候选的 `teclId`、`subjId`、`clroId`、`acteId` 四项均存在且一致。
3. 正式课表日期在北京时间下为同一天，节次相邻，正式时间顺序正确；候选不能倒退、跨天或跳到另一门课。
4. 正式课间长度在明确的有限上限内。建议首版以 **15 分钟**作为待验证的保守上限；本次实际观察到的是 5 分钟，15 分钟不是已确认的站点协议规则。
5. 使用服务器时间和候选的 `liveStartTime`、`liveEndTime` 校验直播窗口。时间缺失、无效或互相矛盾时停止衔接；自动换节不能依靠本机时钟猜测。
6. 候选详情确认登录、观看权限及可用的受支持直播格式。列表只作交叉核验；如果列表与详情矛盾、关联不唯一或必要字段缺失，就停止衔接。

仅凭一次断流、播放器报错或候选已进入直播窗口，不足以结束当前节。应先通过当前节的服务器时间或明确结束状态确认它已结束。`continueCourRefreshTime` 暂作待核实的元数据提示，不能独自触发换节或越过上述校验。

## 触发、反馈与退出

| 触发情况 | 必须读取或检查的反馈 | 下一步或退出条件 |
| --- | --- | --- |
| 当前节音频中断 | 重新核对同一 `courseId` 的直播状态 | 仍在当前窗口内时只做现有的有界重连；登录、权限或格式错误直接停止，不借此跳节 |
| 当前节确认结束 | 当前详情中的候选标识，再读取候选最新详情 | 候选通过全部条件后才进入等待或切换；没有候选、存在歧义或字段不完整则停止 |
| 候选尚未开播 | 服务器时间、候选直播窗口和已验证的有限课间 | 采用可取消的有限等待，到准入时间后重新核验；超出课间上限或候选已结束则停止 |
| 候选允许接入 | 再次检查停止信号，确认旧媒体进程已结束 | 释放旧进程和读取线程，丢弃旧 ASR 未定稿内容及未确认数字片段，再创建候选媒体源 |
| 候选收到有效音频 | 新源确实持续提供可识别音频 | 才将该节记为当前节及已访问标识，继续正常监听 |
| 用户停止、退出或任一必要校验失败 | 当前停止标志及资源释放结果 | 结束等待和监听，关闭相关进程与线程；不再发起下一次请求或创建新媒体源 |

跨节不能把两侧数字片段拼在一起，也不能在断流时通过强制输出旧缓存来生成签到码。已完成的提醒与去重记录保留。所有等待和请求都应有明确上限；等待可立即取消，正在进行的请求结束后必须在任何后续动作前再次检查停止信号。

两节与三节采用同一逐节校验流程：第二节结束后，只有第二节最新详情再次给出合法候选，才验证第三节。禁止预先拼出整天的播放队列，也不使用历史点播地址兜底。

## 后续验证步骤

先进行完全离线的模拟测试，不接入学校或真实媒体：

1. 将两节元数据的关系转为虚构标识、虚构时间的测试样本，使用可控服务器时钟模拟正式结束、直播结束和刷新提示等不同边界。确认它们分别参与正确判断。
2. 覆盖合法两节、逐节发现的三节、无第三节、分页未完整、重复候选、循环关联、四项分组不一致、跨天、倒序、节次跳跃和过长课间。候选不充分时必须停止。
3. 覆盖时间和标识缺失、格式错误、登录过期、无权限及不支持的媒体格式。验证所有请求仍为同源只读请求，不发送观看统计、心跳或注销操作。
4. 用本机合成音频和虚拟媒体源验证：断流只重连当前节，切换前旧进程已退出，跨节 ASR 缓存被清空，第三节也重新验证。不能出现两个媒体进程同时长期运行。
5. 分别在读取候选、课间等待、关闭旧源、创建新源和收到首块音频时取消。验证不会继续请求下一节，不遗留进程或读取线程，也不会因音频不连续而产生跨节识别结果。

模拟测试通过后，再进行受控实测：先对同一教学班的两节课核验最新元数据与服务器时间，记录候选和窗口判断；随后验证一次从当前节结束到候选首块音频的完整交接，检查衔接间隔、识别是否中断以及资源是否释放。第三节必须单独核验其实际关联和课表，不能沿用本次两节的推断。

实测记录只保留必要的课程标识、时间、判断结果、音频连续性与资源统计，不保存媒体链接、请求凭据或账号。本次工作停留在方案阶段；上述模拟与实际换节验证均不代表已经完成。
